Elgar File System And Architecture Map

This page explains the repo before explaining the behavior. Start with the folders, then the crates, then the files, then the flow from your message to verified output.

The one rule to remember
  1. The model suggests.
  2. Elgar validates.
  3. Policy decides.
  4. Executors verify.
  5. The UI reports verified truth.

2. The Three Crates

Think of these as three departments. They talk in one direction: CLI/TUI call core. Core does not call CLI/TUI.

elgar-cli: starts the app
  • Reads command-line args.
  • Finds project root.
  • Loads provider config.
  • Launches TUI or one-shot prompt.
elgar-tui: shows the app
  • Reads terminal input.
  • Handles slash commands.
  • Shows conversation panes.
  • Renders status, memory, tokens, trace.
elgar-core: runs the app
  • Calls provider.
  • Validates tool calls.
  • Applies policy.
  • Executes and verifies file/shell work.

6. The Architecture In One Stack

Read this from top to bottom when tracing a bug.

A
Launch

elgar-cli decides mode and config.

B
Interface

elgar-tui receives input and shows output.

C
Runtime

agent_runtime.rs and agent_loop.rs coordinate.

D
Provider

LM Studio or stub returns model output.

E
Validation + policy

Tools become typed actions, then policy decides.

F
Execution

fs.rs and shell.rs do real work.

G
Truth

Session and logs store what actually happened.

Debugging rule

If you are lost, do not start in agent_loop.rs. First decide which layer owns the problem: launch, TUI display, provider, policy, executor, session, or logs.

The file layout exists to keep those layers separate. Some files are still too large, especially agent_loop.rs, but the ownership model is the guide.

Suggested study order: repo map, three crates, main files, plain chat flow, file-work flow, LM Studio flow.
